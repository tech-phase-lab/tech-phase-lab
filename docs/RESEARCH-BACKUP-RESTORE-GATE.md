# 研究DBバックアップの完了条件

実装を含む最新ソースは[2026-10-24の外部保管・実復元](EXTERNAL-SOURCE-BACKUP-2026-10-24.md)で確認済み。
これはソースの記録であり、本番研究DBの保存実績ではない。

`scripts/tech-phase/external_research_backup.py` は、保存した暗号文を取得し直し、
その取得ファイルから隔離復元できた場合だけ完了manifestを保存する。
従来はサイズとSHAの読み戻し照合までが保存処理で、復号・DB検査は別操作だった。

## 処理順

1. 元DBのWALを含めSQLite online backupで全テーブルを取得。
2. 必須テーブルと整合性を検査し、AES-256-GCMで暗号化。
3. 暗号文を条件付き保存し、同じobjectを上限付きで取得。
4. 取得したファイルのサイズ/SHA、認証タグ、復号後のSHA、DB整合性と必須テーブルを検査。
5. 検査成功後にmanifestを条件付き保存し、その読み戻しも照合して成功を返す。

復元検査に失敗した場合はmanifestを作らず、暗号文を自動削除しない。
manifestの通信・読み戻し失敗でも処理成功にはしない。
一時ファイルはprivateディレクトリ内に置き、通常終了と例外時に片付ける。
追加の取得リクエストはなく、従来の読み戻しバイトをファイルに保存して検査する。
一時領域には元スナップショット、暗号文、取得暗号文、隔離復元DBが共存するため、
DBサイズのおよそ4倍とSQLite検査用の余裕が必要。1GiBの元DB上限は変えていない。

## 証拠の範囲

`restore_verified=true` はその取得バイトからの研究DB復元検査だけを表す。
`full_site_recovery_verified=false` は維持する。会員ログイン、API、外部画像、
PayPal状態、RESOLUTEの削除・通知停止履歴、本番保存開始の受入ではない。
過去のmanifestを書き換えず、過去の保存を検査済みへ格上げしない。

変更の検証には合成SQLiteデータ、実AES暗号化、メモリ内の保存先を使用する。
WAL内の会員メモ復元、保存先から取得したファイルの使用、manifest公開順序、
破損した読み戻し、暗号鍵の不一致、一時ファイルの片付け、manifest照合失敗を確認する。
本番R2への研究DB保存・復元の実績ではない。

## 本番で残る条件

保存先設定は通信前に検査する。HTTPSのCloudflare R2アカウントendpoint（標準・EU・FedRAMP）、
ポート省略または443、既存バケット `resolute-backup-external`、region `auto` の組み合わせだけを受け付ける。
別ホスト、別バケット、URL内の認証情報・パス・query・fragment・制御文字は拒否し、SDK clientを作成しない。
これは設定の取り違え対策であり、正しいCloudflareアカウントか、キーの権限がそのバケットだけかの実証ではない。
実アカウントと最小権限の照合は依然必要。既存キーの再生成や本番変数の変更は行っていない。

[実一覧の記録](EXTERNAL-DATA-INVENTORY-2026-10-24.md)では、既知の研究DB保存先は0件。
元DBを読める環境へのこの処理と既存鍵参照の配置が未完了で、現在のresearchイメージに
自動同梱されない。Railway管理への再接続・鍵再入力は試さず、朝ジョブも変更していない。
元データにアクセスできる段階で実行し、実ログと保存結果を確認する必要がある。
保存ゲートはOFF、使用済みAI診断claimは保持。Render待機先は別工程として残す。
