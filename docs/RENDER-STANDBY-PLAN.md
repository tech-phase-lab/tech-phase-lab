# Railway障害時の予備環境（Render）

2026-10-23 JST、オーナー確認。Renderを忘れずに後続作業として扱う。
Railwayから全面移行する方針ではなく、障害時に復旧先を確保する目的。
現時点ではRenderの契約、常時稼働サービスの作成、課金変更は行わない。

## 進める順序

1. Tech Phase全体のソースと依存ライブラリを暗号化してRailway外へ保管し、
   実際にダウンロード・復号・復元・ビルドを確認する。
2. 最新の本番DBと削除・通知停止履歴について、完全な一覧と保存結果を確認し、
   隔離環境への復元を検証する。初期の空一覧や古いバックアップで代用しない。
   AI診断の実行済み記録も保持し、復元後の追加AI実行を防ぐ。
3. Render向けの起動設定、必要な環境変数の「名前」、接続・切替・戻し方を準備する。
   秘密の値はGitやバックアップ内の設定ファイルに書かない。
4. 予備環境で復元・動作確認し、実測した復旧時間とデータの復旧時点を記録する。
   費用を伴う契約・稼働開始は別途具体的な構成を確認してから行う。

## 切替で必要な条件

アプリだけRenderに置いても、DBが停止したRailwayにしかなければ復旧できない。
DBの復元先とアプリからの接続を含めて確認する。切替時は旧環境の書き込みと
ジョブを停止または遮断し、二重実行を防ぐ。朝ジョブの設定・確認予約は今回変更しない。
決済、通知メール、追加AI呼び出しは復元試験で実行しない。

バックアップから起動する方式には復旧待ち時間とバックアップ以降のデータ差がある。
「どちらかが止まっても無停止」の実現はまだ未検証。自動切替・二重書き込みを
先に導入せず、まず安全に取り出して動かせる予備環境を作る。

現在、Railway接続の再試行やログイン要求はしない。既に完了したパスワード更新、
変数入力、デプロイ、復旧鍵保管、1回のAI接続試験をやり直さない。

## 予備環境に移す対象の確認表

2026-10-23のリポジトリ内Dockerfileから確認した起動単位。実稼働中の構成を
Railwayから読み直した結果ではない。Render側の設定はまだ作成・反映していない。

| 対象 | 既存の起動定義 | 復元で別途必要なもの |
| --- | --- | --- |
| フロントエンド | ルートの `package.json`（`npm run build` / `npm start`） | 同じlockfileと対応するNode環境。今回の依存保管の対象 |
| RESOLUTE API | `services/resolute-api/Dockerfile`（リポジトリ全体をビルド対象にする） | API専用lockfileの依存、DB、認証設定。Node24系 |
| 削除・通知停止履歴の保管 | `services/resolute-protection/Dockerfile`（同上） | 完全な最新履歴一覧、書き込み停止の確認、保管先設定 |
| リサーチ・ニュース監視 | `Dockerfile.research-monitor`（同上） | Python依存、`/data` のSQLite全体、外部接続設定 |
| 決済連携 | `services/tech-phase-billing/Dockerfile`（同サービス内をビルド対象にする） | 専用依存と決済台帳。復元試験では本番処理を無効にする |
| DBバックアップ | `services/tech-phase-backup/Dockerfile`（同サービス内をビルド対象にする） | DB接続先の見直し、PostgreSQLツール、Python依存、既存の復旧鍵 |
| 隔離復元検査 | `services/resolute-recovery/Dockerfile`（リポジトリ全体をビルド対象にする） | 検査専用の隔離DB。本番サービスとして常時起動しない |

API、決済、Python監視はそれぞれ別の依存セットを持つ。
フロントエンドのライブラリを保管しただけで全サービスの復旧完了にはしない。
コンテナのベースイメージやNode実行ファイルも今回の依存アーカイブには含まれない。

DBバックアップ処理には `postgres.railway.internal` の接続先指定があるため、
Renderでそのまま動くと判断しない。復旧先DBへの最小権限接続と隔離復元を
確認してから切り替える。秘密の値や現在のジョブ設定はこの表に書き出さない。
