# 運用の手順書：鍵の一覧・作り直し・障害時の対応

作成：2026年10月22日（Railwayの環境変数流出の可能性の通知と、ビルド停止を受けて）
対象：Tech Phase Research（Vercelのサイト／Railwayの監視・RESOLUTE・課金）

> **この文書に、鍵やパスワードの値は書かない。** 名前と、置き場所と、手順だけを書く。
> 画面の名前は、各サービスの更新で変わることがある。見つからないときは、画面の写真（鍵が映らないもの）を見せて相談する。

## 1. 今回（10月22日）の経緯

- Railwayが、環境変数（暗号化して保管している鍵など）が第三者に見られた可能性を通知。
- 同時に、Railwayのビルド（新しい版を作る作業）が世界中で停止。Enterprise → Pro → Hobby の順で再開。

- 対応：下の「5. 実施記録」を参照。

### 値の見分け方（Railway）

- `${{ サービス名.変数名 }}` で始まる：別のサービスから**自動でもらっている**。ここは触らず、元（バケツなど）を直す。
- 長い英数字の並び：**自分で入れた値**。新しい値に貼り替える。

## 3. 鍵を作り直す共通の手順

1. 新しい鍵を作る（値はその場で1回だけ表示されることが多い。コピーして貼る。チャットや写真には出さない）。
2. Railway（とVercel）の該当の変数を、新しい値に貼り替えて保存する。
3. **古い鍵を削除（無効化）する。**
4. 反映のために、該当サービスを再デプロイする（Railwayの復旧後。変数を貼り替えただけでは、動いているサービスに反映されない）。
5. 動作を確認する（ログにエラーが出ていないか／バックアップなら `BACKUP_OK`）。
6. 利用量に不審な増え方がないか、各サービスの画面で見る。

作り直しの順番は、被害が大きい順（上の表の「高」から）。

## 4. 障害時（Railwayが止まったとき）の手順

### 4-1. まず状況を見る
- Railwayの状況ページ（status.railway.com）：どのプランのビルドが止まっているか、再開の時刻。
- サイトに「情報の取得に遅れが出ています」「情報の取得先に接続できていません」と出ていれば、取り込みが止まっている（2026年10月22日に追加した表示）。

### 4-2. 止まっているときにやらないこと
- 変数を何度も書き換えない。デプロイを何度も押さない。
- Postgresのサービスの変数を、手で書き換えない（実際のパスワードは変わらず、つながらなくなる）。

### 4-3. 復旧後にやること（順番）
1. 監視（research-monitor-staging、research-monitor）を再デプロイする（Redeployが使えないときは、サービスの画面で Ctrl/Cmd + K →「Deploy Latest Commit」）。
2. バックアップ（resolute-backup）で「Run now」を押し、`RESOLUTE_BACKUP_OK` を確認する。課金側のバックアップも同様。
3. 目標株価、ハイテク速報の決算タブなど、止まっていた機能を画面で確認する。
4. 失敗していた処理（復旧の処理など）が、成功に戻ったか確認する。

### 4-4. 影響の整理（Railwayが止まったとき）
- 止まる：新しい版の反映、環境変数の反映、Xの取り込み、翻訳・AI要約、バックアップ、定期処理。
- 影響しない：サイト本体（Vercel）の表示、保存済みのデータ、GitHub、ログイン。

## 7. 待機環境への切り替え（案）

- 目的：来年の本番で、Railwayが数日止まっても、購読者への影響を小さくする。
- 方針：普段は動かさない待機用を、別の事業者に用意しておく。障害時だけ起動する。
  1. バックアップを、Railway以外にも置く（暗号化したうえで）。
  2. 監視の処理は、Dockerで作ってある（`Dockerfile.research-monitor`）。別の場所でも立ち上げられる。
  3. サイトから監視へのつなぎ先（URL）を、1か所で切り替えられるようにする。
  4. 切り替えの手順を書き、事前に1回、予行演習をする。
- 二重で同時に動かすことはしない（Xの利用量やOpenAIの料金が倍になる、記事が重複するなどの問題があるため）。
