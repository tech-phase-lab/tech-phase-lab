# 復旧設定の照合表（値を保存しない）

2026-10-23 JST。Railway障害中は接続・再ログイン・再認証を試さない。
ユーザーが作成済みのR2バケット/接続キー、変更済みのパスワードや保管済みの鍵を
再作成・再入力させない。本書は設定値のバックアップではなく、復旧時の照合項目である。
現在の稼働環境との差分は復旧後に読み取り確認する。

環境変数名と参照ファイルを `configuration-names.json` に抽出する。値は読まない。
6c0ebd8aでは206名を検出した。テスト用や退役コードの名前も含み、動的な変数名は
抜ける可能性がある。これをそのまま本番へ一括登録する用途ではない。

## ソースだけでは保存できない設定

Railwayの全サービスについて、復旧後に以下をサービス単位で照合する。
値の保管は暗号化された別経路で行い、この文書・Git・チャットに書かない。

- 稼働コミット、Dockerfile、開始コマンド、作業ディレクトリ、内部/外部ポート、healthcheck。
- volumeのID、mount path、容量、所有者、DB以外のファイル。bucketの実体とデータ量。
- 変数の名前、設定先、参照元、変更後の稼働反映状態。共有参照を平文へ置換しない。
- Cronの式/タイムゾーン、再試行、再起動、停止条件。既存朝ジョブ/確認予約は変更しない。
- ドメイン・DNS・TLS・入口の向き先。Vercelの一時停止は維持。
- Webhook登録先と識別子。PayPal・Clerkからの再送で二重処理されないこと。
- 外部監視のチェック名、対象ジョブ、通知先と停止状態。確認のためのメール送信はしない。

Clerk会員export、PayPal状態、Google側の会員同期、外部画像の実体はGit bundleに含まれない。
各サービスの取得/再構築可能範囲を確認するまで「全部保管済み」としない。

## オフラインで確認済みにできる範囲

1. コードとGit管理画像を履歴付きbundleにまとめ、空repoへ復元してcommit/tree一致を確認。
2. ローカルの未追跡ファイル・秘密設定をbundleへ混入させない。
3. DBや履歴の復元テストは合成データで実行。実データ保管の証拠と分離。
4. この照合表と変数名一覧を用意し、障害復旧後の不足確認を短縮する。

実行手順（出力はprivateなローカルディレクトリ。自動アップロードしない）:

```sh
python3 scripts/tech-phase/prepare_source_recovery.py --repo /path/to/clean-checkout --commit FULL_COMMIT_SHA --output /private/new-source-package
python3 scripts/tech-phase/prepare_source_recovery.py --verify /private/new-source-package
```

出力は `source.bundle` / `manifest.json` / `configuration-names.json`。
暗号化・外部転送はまだしない。bundleは履歴も含むので、外部保管前に秘密混入の有無を
確認し、復旧鍵を独立保管したうえで暗号化する。Git LFSのpointer・symlink・submoduleは
実体不足を黙認せず失敗する。未コミット変更や出力先の上書きも拒否する。

## Offline source encryption (2026-10-23 JST)

`scripts/tech-phase/seal_source_recovery.py` seals the three-file source package
with AES-256-GCM and verifies decryption into a disposable directory and Git
restoration before publishing the encrypted file. It never contacts Railway or
R2. Existing destinations are rejected rather than overwritten.

Supply the independently retained `TECH_PHASE_EXTERNAL_KEY_HEX` through a secure
local environment (32 bytes, 64 lowercase hexadecimal characters); never paste
the key in chat or command arguments. This is the external-backup encryption
key, not an R2 access secret or a replacement for the existing RESOLUTE key.
No production key was generated by this change.

```sh
python3 scripts/tech-phase/seal_source_recovery.py --package /private/source-package --output /private/source.aesgcm --expected-commit FULL_TRUSTED_COMMIT_SHA
python3 scripts/tech-phase/seal_source_recovery.py --verify-archive /private/source.aesgcm --expected-commit FULL_TRUSTED_COMMIT_SHA
```

The expected commit must be retained independently of the archive. It is bound
to authentication and compared with the restored Git commit. Only the three
regular package files are accepted; links, duplicate members and traversal
paths are rejected. Maximum plaintext archive size is 1 GiB.

This verifies source recovery only. It does not contain live databases, provider
secret values, external image payloads or Clerk/PayPal account state.
`external_storage_verified` and `runtime_restore_verified` remain false.
R2 upload/readback and key custody are separate unfinished steps.

## Source upload and readback (2026-10-23 JST)

`upload_source_recovery.py` combines sealing, conditional R2 upload, full bounded
download, authenticated decryption and isolated Git restore. The completion
manifest is uploaded last and itself read back. Success means source recovery
from downloaded bytes, not whole-site/runtime recovery.

Required secure environment: existing five `MIRROR_DESTINATION_*` variables
(ENDPOINT, BUCKET, REGION, ACCESS_KEY_ID, SECRET_ACCESS_KEY), independently retained
`TECH_PHASE_EXTERNAL_KEY_HEX`, and `TECH_PHASE_SOURCE_UPLOAD_ENABLED=true`.
Default is disabled. Only HTTPS R2 endpoints are accepted. The existing
`resolute-backup-external` bucket can be used with region `auto`; no new bucket
or token is needed. Keep secrets out of command arguments/chat/repository.

```sh
python3 scripts/tech-phase/upload_source_recovery.py --package /private/source-package --expected-commit FULL_TRUSTED_COMMIT_SHA
```

Dependencies are already pinned in services/tech-phase-backup/requirements.txt.
Objects use tech-phase/source/v1/<commit>/<cipher-sha256>.aesgcm plus .json.
No latest pointer, public ACL, deletion, retention/cron change or deployment.
Every PUT uses IfNoneMatch=*. A failed run may leave an orphan encrypted object;
it must not be considered verified or automatically deleted. Re-running sealing
uses a fresh nonce and therefore a new object and incurs another upload.

Implementation/tests use fake storage and disposable keys. Actual R2 credentials
and an independently retained external-backup encryption key are not available
in the current execution environment; no real R2 upload has been performed.

methods. Subsequent field inspection was denied by automatic safety review,
which reported unapproved accounts.google.com access without a user-selected
method. No method was selected by the assistant and no credentials were entered.
Do not bypass or retry that access. Ask the owner which sign-in method they use
