# 待機環境（フェイルオーバー）の計画

作成：2026年10月22日
目的：来年の本番で、Railwayが数日止まっても、購読者への影響を小さくする。
前提：費用を減らすことが第一。普段は動かさない「待機用」を用意し、障害のときだけ立ち上げる。

> この文書は計画。実際の立ち上げ（デプロイ）はしていない。値（鍵など）は書かない。

---

## 1. 何を切り替えるのか

| 構成要素 | いまの場所 | 障害時 |
|---|---|---|
| サイト（画面） | Vercel | 影響なし。そのまま使える |
| 監視（ニュース・X・翻訳・目標株価などの取り込み） | Railway | **待機用に切り替える対象** |
| データ（監視が持つ状態） | Railwayの保存用ディスク（`/data`） | 外のバックアップから、待機用に戻す |
| バックアップ | Cloudflare R2（ChatGPTと進行中）、RESOLUTE・課金はRailwayのバケツ | 外のR2を、復元の元にする |
| ログイン（Clerk）、決済（PayPal） | 各サービス | 影響なし |

切り替えるのは、**監視だけ**。サイトには、手を入れずに済む。

## 2. 切り替えの仕組み（確認済み）

サイトは、監視の場所を、Vercelの環境変数 `RESEARCH_MONITOR_URL`（と、合言葉 `RESEARCH_MONITOR_TOKEN`）で**1か所だけ**指定している。ニュース、目標株価、決算、ウォッチ、通知など、約20のAPIが、この1つを使っている。

つまり、待機用の監視を立ち上げたら、**この2つの変数を書き換えて、Vercelを再デプロイする**だけで、サイトの向き先が切り替わる。コードの変更は要らない。

> 将来の改善案：Vercelの再デプロイを待たずに切り替えるため、向き先を、Vercelの「Edge Config」などに置く。手間が増えるので、公開後でよい。

## 3. 待機用に使う事業者の比較

| | Render | Fly.io |
|---|---|---|
| Railwayとの近さ | **近い**（Git連携、Dockerfile、環境変数、定期実行、保存用ディスク） | 少し技術寄り（コマンド操作が中心） |
| 立ち上げの難しさ | 画面で操作できる。やさしい | CLIが基本。やや難しい |
| 保存用ディスク | 1GBあたり月0.25ドル（公式の料金ページより） | ボリュームは1GBあたり月0.15ドル |
| 普段の費用の抑え方 | 待機用を「一時停止」しておく（停止中の課金は、要確認） | 機械を**停止**しておくと、計算の料金がかからない（ディスクと保存分のみ） |
| 本体の費用の目安 | 公式の料金ページで確認 | 最小の機械（512MB）が、動かした場合で月3.69ドル程度 |
| 向いている人 | 画面で完結させたい | 費用を最小にしたい、コマンド操作に抵抗がない |

**おすすめ：Render。** 理由は、Railwayと使い心地が近く、お一人での運用に、やさしいため。費用が最優先で、操作に慣れてきたら、Fly.ioも、検討する。
最新の料金は、契約の前に、各社の公式ページで確認する。

## 4. 待機用を立ち上げる手順（障害のとき）

最初の1回は、30分〜90分を見込む（予行演習でその時間を測る）。

1. **障害の確認**：Railwayの状況ページで、止まっていること、復旧の見込みを確認する。数時間で戻る見込みなら、待つ。
2. **待機用の監視を起動する**：Renderで、`deploy/render-standby.yaml`（ブループリント）をもとに、サービスを作る。環境変数は、手元の鍵の一覧（`docs/OPERATIONS-RUNBOOK-2026-10-22.md`）を見て、画面で入れる。
3. **データを戻す**：外のバックアップ（R2）から、最新の暗号化バックアップを取り出し、待機用の `/data` に戻す（手順は、ChatGPT側で整備中のバックアップ手順に合わせて、ここに追記する）。
4. **動作確認**：待機用の `/livez` が応答すること。ログに、取り込みが動いている記録が出ること。
5. **サイトの向き先を切り替える**：Vercelの `RESEARCH_MONITOR_URL` と `RESEARCH_MONITOR_TOKEN` を、待機用のものに書き換え、再デプロイする。
6. **サイトで確認する**：ニュース、目標株価、決算タブが更新されること。「遅れています」の表示が出ていないこと。
7. **元に戻すとき**：Railway復旧後、同じ手順で、向き先を戻す。待機用は、停止する。**二重で同時に動かさない**（Xの利用量とOpenAIの料金が倍になる、記事が重複するため）。

## 5. 準備しておくこと（公開前）

- [ ] Renderのアカウントを作り、請求の設定をしておく（使わなくても、いつでも立ち上げられるように）。
- [ ] 待機用のサービスを、**一度作って、起動できることを確認**し、そのあと停止する（予行演習）。
- [ ] 予行演習で、切り替えにかかった時間を、この文書に記録する。
- [ ] 外のバックアップ（R2）から、**実際に復元できる**ことを、一度確認する。
- [ ] 待機用に入れる鍵は、Railwayとは別に新しく作る（同じ鍵を、複数の場所で使い回さない）。
- [ ] 暗号化の鍵を、**Railwayの外**（パスワード管理アプリ、紙など）に、安全に保管する。

## 6. 費用の見方

- 普段（停止中）：ディスク代程度（数十円〜数百円/月）に抑えられる見込み。
- 障害中（起動中）：事業者の小さなプランで、月数ドル相当（日割り・秒単位の課金の事業者もある）。
- 参考：Railwayの**Proプランは月20ドル（Hobbyは5ドル）**。プランを上げても、今回のようなRailway全体の障害には、半日程度かかる（復旧の順番が早くなるだけ）。待機用を別に持つほうが、本番の安心につながる。

## 7. 限界

- 切り替えには、**人が動く時間**（数十分〜）がかかる。「瞬時」ではなく、「数十分〜数時間」。
- 瞬時に切り替えたいなら、**常に2か所で動かす**構成が必要。費用と複雑さが増える。公開後、会員数や収益に応じて、検討する。
- この計画は、監視（Railwayで動いているもの）の切り替えを対象にしている。RESOLUTEや、課金（試験用）は、別途検討する。
